## 1. The InfBench "256k cliff" was a measurement artifact — root cause

`outputs/eval/infbench_lengths.json` (v1) keyed instances by bare dataset id;
ids collide across the three ∞Bench subsets, so each task's pass overwrote the
others' lengths — the cache was collision soup (final pass = kv's ~124k-tables).
The plugin's `[0.5, 0.92]×target` band filter therefore selected nonsense pools:
the "128k" cells actually served 143k/223k/266k-token prompts while the "256k"
cells served 131k–163k (verified: server-side `prompt_tokens` vs recalibrated
true lengths `infbench_lengths_v3.json`, task/id-keyed, chars/token 3.5–6.5 sanity-checked).

Historical rows re-attributed to TRUE lengths (`infb_forensics.py`):

```

infb_bookmc      120-160k  3       0       1      0
infb_bookmc      160-200k  1       0       0      0
infb_bookmc      200-240k  1       1       1      0
infb_bookmc      240-280k  1       0       0      0

infb_codedebug     40-80k  1       1       1      0
```

Reads: bookmc is **non-monotone in true length** (misses at 120–160k AND
240–280k, all hits at 200–240k) — instance difficulty dominates, no cliff;
one case-miss (gold contained case-insensitively) and one 1024-token budget
drain inflated the original zeros; codedebug 160–200k is 0/9 strict across
stock + both qk arms — the only zone the historical data flags as possibly
real. kv never varied length (fixed ~124k tables → flat 1.000 everywhere).

## 5. Verdicts (cliff / no-cliff, per axis)

## 6. Method notes / caveats

- v1/v2 length caches were corrupt (id collisions; v2 also hit a tokenizer
  wrapper quirk) — v3 is task/id-keyed, chars/token sanity-asserted in the plugin.
- Case-sensitive scoring is primary (contract); case-insensitive reported as
  ci-hits where it differs. Budget drains flagged, not silently scored.
- n=3/cell bands: ±\>50pt CIs on single bands; conclusions rest on patterns
  across bands + greedy confirmation, never a single cell.
